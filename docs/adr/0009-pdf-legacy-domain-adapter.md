# Safe PDF Serialization-to-domain adapter boundary

Status: Accepted architecture (RP-103, 2026-09-27); adapter, downstream migration, and parser integration deferred. This follows [ADR 0008](0008-pdf-serialization-boundary.md). The legacy PDF parser remains authoritative at runtime and `NO_PRODUCTION_SHADOW` remains active.

## Production downstream audit

| Seam | Actual input -> output | Page/line boundary and whitespace behavior |
| --- | --- | --- |
| [`reconstructPdfPage`](../../src/parsers/pdfPageReconstructor.ts) / [`pdfLineReconstructor`](../../src/parsers/pdfLineReconstructor.ts) | PDF text items plus page context -> one page `string` | Legacy reconstruction iterates the supplied items, groups them using y position and `hasEOL`, trims items, joins fragments with spaces, and joins reconstructed lines with `\n`. These are legacy layout decisions, not Serialization V1 authority. |
| [`parsePdfResume`](../../src/parsers/pdfResumeParser.ts) | `File` -> `Promise<ParsedResumeFile>` | Requests PDF.js pages `1..numPages`, reconstructs each page string, then `pages.join('\n\n')`. Only `pageCount` survives as metadata; page identity and the distinction between source newline and inserted page separator do not. |
| [`parseResumeFile`](../../src/parsers/resumeFileParser.ts) | `File` -> `Promise<ParsedResumeFile>` | Routes PDF/DOCX. `ParsedResumeFile` requires `text: string`, filename, file type, optional page count, and parser messages. It counts non-whitespace characters globally and currently maps short PDF text to legacy `SCANNED_PDF` and shorter text to `PARSE_FAILED`; those coarse outcomes are not new-pipeline evidence or adapter policy. |
| [`resumeService.analyzeResume`](../../src/services/resumeService.ts) / [`normalizeResumeText`](../../src/parsers/normalizeResumeText.ts) | `ParsedResumeFile.text: string` -> normalized whole-document `string` | The service passes that string, alongside metadata, to `resumeAnalyzer.analyze`. Normalization rewrites line endings, controls, bullets, spaces/tabs, line edges, and repeated newlines. No page boundary type exists. |
| [`detectResumeSections`](../../src/analyzers/sectionDetector.ts) | complete normalized `string` -> `{ sections: Partial<Record<ResumeSectionKey,string>>, preamble: string[], detectedSections }` | Splits on `\n`; recognizes whole-line heading aliases or colon-inline headings, with a middle-dot special case. Reassembles each section body with `\n`. An unrelated prefix can prevent a heading match. It cannot distinguish an inserted newline from one in source text. |
| [`resumeAnalyzer.analyze`](../../src/analyzers/resumeAnalyzer.ts) | `ParsedResumeFile` plus normalized `string` -> `ResumeProfile` | Detects sections and skills from the whole string; name from preamble; work, education, and projects from optional section strings split again on `\n`; education has a whole-text line fallback; career direction and warnings inspect whole text. The profile carries page count only in metadata. Random profile ID and current timestamp mean whole-profile determinism is a separate concern from adapter determinism. |

The domain subparsers currently accept `string | undefined`, not pages, units, or typed lines: `parseWorkExperiences`, `parseEducation`, and `parseProjects` split section strings on `\n` and apply domain-specific rules. `detectSkills` accepts a single string. The current pipeline therefore **requires flat strings**, and current line boundaries are partly reconstructed, not necessarily source-authored. Page boundaries are destroyed by `pages.join('\n\n')`; `pageCount` alone cannot restore them. Explicit pages are useful for preventing accidental cross-page token or heading fusion even though the current domain APIs do not consume them.

## Decision: a new structured downstream seam

Choose **NEW_DOWNSTREAM_SEAM (Option C)**, not direct use of the current flat-string API. A `SAFE_LEGACY_ADAPTER` that joins pages with `\n` or `\n\n` would turn structural metadata into text characters that `detectResumeSections` and the domain parsers treat as semantic line delimiters. The current APIs have no out-of-band delimiter channel. No rule in Reading Order or Serialization authorizes a page/unit join character, and one VisualGroup or SerializedUnit is not a text line. Reusing the legacy separator would silently import legacy reconstruction policy. The current downstream string contract cannot be preserved unchanged for a complete multi-page `SerializedDocument` without that unsupported choice.

The smallest safe adapter is a guarded, mechanical projection from a runtime-valid, fully resolved `SerializedDocument` to a typed **`ResumeSourceDocument`** that retains ordered pages and their ordered units, with exact `text` and page/group/run provenance. It may defensively copy data but must not change any unit string, infer a separator, flatten pages, or sort by input-array accident. It consumes the RP-102-validated canonical page order, not an arbitrary caller array order. It must use RP-102's `canRunLegacyResumeAdapter` document admission with the validated canonical page manifest and bound page results; bypassed or malformed input is rejected, never repaired. It must not mutate the source document or inspect geometry; the same admitted document must yield the same adapter output regardless of upstream scale or translation. This output remains functional private data. No raw text, filename, font, exception detail, or contact/identity data belongs in adapter diagnostics; stable code, page, and counts suffice.

The *new downstream seam*, separately designed and tested before integration, should consume typed pages/units rather than a fabricated whole-document string. It can expose source-embedded `\n` as an explicit source break and page boundaries as a distinct `PAGE_BREAK` event, without inserting `\n` into `text`; a unit boundary by itself is **not** a line break. A segment between source-authored breaks is not automatically a visual line. Section state may continue across pages, but heading recognition may use only actual source-delimited segments or later approved structural evidence. If one run contains several apparent headings without source delimiters, the seam must not split them by guessed layout or resume vocabulary. That recognition gap remains unresolved, not an adapter fallback trigger.

This requires a minimal input migration, **not a new work/education/project recognition policy**: add a structured entrypoint for section detection, pass source-delimited segments to work/education/project parsing instead of manufacturing section strings with `join('\n')`, and evaluate global consumers (`detectSkills`, education fallback, career direction, warning counts) over explicit segments/pages without cross-boundary matches. Existing domain regexes and field rules can largely remain; their `string`/`split('\n')` wrappers cannot remain the sole entrypoints. The migration needs anonymous cross-page and source-newline contracts before any authoritative switch. `resumeAnalyzer.analyze(parsed, normalizedText)` and the DOCX path stay unchanged until then.

## Separator and normalization ownership

| Transformation | Ownership decision |
| --- | --- |
| Canonical `SerializedTextUnit.text` | Functional source payload. Adapter preserves its JavaScript string exactly, including empty text, spaces, tabs, CR/LF, and Unicode. |
| Page or unit boundary | Structural metadata. Adapter inserts **no** whitespace/newline and creates no textual join. A later structured consumer can see a typed page break without mistaking it for resume content. |
| Existing NFKC, CRLF/control/bullet transforms | Existing whole-string normalization, plausibly lexical in intent but not automatically lossless. Any future per-unit application requires its own approved contract and tests; none is moved into the adapter here. |
| Existing trim, tab/space collapse, repeated-newline collapse, legacy fragment/line/page joins | Structural/layout normalization. Not inherited by the adapter. |
| Heading aliases, middle-dot section splitting, name/work/education/project/skill recognition | Section/domain behavior. Not performed or repaired by the adapter. |

There is **no approved flat-string separator** for this boundary. Source-internal newline is authoritative data; a typed page break is a structural delimiter outside text; a newly inserted newline would be unsupported inference because current downstream parsing cannot distinguish it from source text. The selected adapter output is structured, so a flat string is **not required by the new seam**, although it is required by the unmodified legacy one.

## Result, cause, and integration boundary

The adapter makes no evidence decision once RP-102 admission succeeds. It does not need a new three-state result or parser cause: a valid admitted document projects mechanically, while a bypassed/invalid document is rejected as a contract failure, not `INSUFFICIENT_EVIDENCE` or AI eligibility. Lack of recognizable sections is a later domain-analysis concern, not a new adapter fallback trigger. No partial `ResumeProfile` or page-level deterministic/AI merge is authorized.

A later, explicit PDF-only authoritative transition is: PDF.js page extraction -> approved page evidence / VisualGroup / Spatial facts -> Reading Order -> Serialization -> document composition -> guarded structured adapter -> structured section/domain input -> `ResumeProfile`. It must replace the PDF branch's legacy [`reconstructPdfPage(...)`](../../src/parsers/pdfResumeParser.ts), `pages.join('\n\n')`, and flat `ParsedResumeFile.text` handoff, and review the PDF-side global low-text/error mapping in `parseResumeFile` plus the service's whole-string normalization/analyzer call. It must not run legacy and new reconstruction in production for comparison. The independently routed [`parseDocxResume`](../../src/parsers/docxResumeParser.ts) and its current string path remain untouched.

Two-column and sidebar cases normally stop at Reading Order V1 before this adapter; same-Y separate columns may stop at VisualGroup; split CJK heading may or may not reach Serialization but receives no repair here; the public PDF remains a later integration reproducer. The five known reconstruction failures remain owned by their existing upstream/integration work. This ADR opens no PDF layout research, parser integration, routing orchestration, AI, or provider selection.
